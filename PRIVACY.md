# Intake privacy and telemetry requirements

**Engineering policy, not deployment evidence.** The standalone service is implemented and synthetically verified locally as recorded in [docs/verification.md](docs/verification.md); it is not provisioned or approved for real-data use. The operator selected Go/PocketBase on a separate Tinfoil instance, accepted no scheduled backups and brief replacement downtime, and requested OpenTelemetry/Honeycomb under the gateway's privacy policy. Stripe and Monero remain future scope. No credentials, destination changes, dashboard creation, export, or production integration are authorized by this document.

## Authority and scope

Read this file before changing instrumentation, logging, tracing, SDK defaults, metrics, collectors, diagnostics, dashboards or deployment. The sibling gateway's [PRIVACY.md](../possums/PRIVACY.md) remains authoritative, particularly [data boundaries](../possums/PRIVACY.md#data-handling-boundaries), [forbidden telemetry](../possums/PRIVACY.md#telemetry-permitted-signals-and-forbidden-data), [aggregation](../possums/PRIVACY.md#aggregation-is-necessary-not-sufficient), [processor/retention controls](../possums/PRIVACY.md#processors-retention-access-and-shutdown) and [verification](../possums/PRIVACY.md#required-evidence-for-every-telemetry-change). Preserve the stricter requirement if documents conflict. The gateway's live evidence is not evidence for this Go service.

These restrictions apply to real data in every environment. A Honeycomb destination named test/dev is not evidence that traffic is synthetic. Synthetic testing requires isolated fake accounts, credentials and payment fixtures, with no real customer/provider data.

## Accounting and processor boundaries

- Persist only account totals, necessary reservations and bounded idempotency/terminal records described in [PLAN.md](PLAN.md), plus the explicitly approved customer-auth state below. Never receive prompts, responses, tools, conversation history or inference model/token metadata. Client recovery credentials remain excluded except for the narrow intake-only transient customer-key operation below; accounting calls must never carry them.
- Accounting JSON parsers ignore additive unknown fields for compatibility, without binding/persisting/echoing/exporting them. A malformed or newer caller may supply extras transiently within the bounded body; ignoring them is not permission for the gateway to send content, credentials or unnecessary request metadata. Known fields alone enter custom accounting. Custom accounting and telemetry allowlists remain closed; native administration follows the separately selected trusted-admin policy below.
- Necessary accounting is not telemetry. Account-scoped balance responses are first-party data; they are not support artifacts or observability exports.
- The encrypted disk/WAL/deleted pages and optional manually downloaded snapshots are persistence boundaries. Deleting a row is not secure erasure. No scheduled backups or external backup destination by default.
- Optional manual snapshots contain sensitive accounting and potentially PocketBase authentication/settings state. Downloading moves that state outside the enclave. No automatic uploads, support bundles or routine financial restore claims.
- Tinfoil controls infrastructure/networking and can observe metadata and disk access patterns. Customer-key-encrypted volumes are beta and do not detect rollback of old valid state. Attestation exposure does not establish verification, freshness, storage unlock, absence of retention or immunity to legal process.
- Future Stripe processing introduces provider/payment metadata outside the enclave. Monero introduces wallet/key, confirmation and chain-observation boundaries. Define and approve those retention/replay requirements separately; do not collect payment history now in anticipation.

## Trusted intake manual-admin exception

Deletion, identity/schema changes and restores can corrupt accounting, lose replay evidence, cause financial rollback or prevent strict startup validation. This is accepted admin authority, **not** safe financial recovery, routine production-restore authorization or permission to discard SQL constraints/reset state. Production and real-data/integration/persistence/resource qualification remain separate.

Admin-vault/customer-admin records are first-party application data, distinct from diagnostic/support artifacts; native stock access is not a new customer-account/role framework. It does not authorize customer inference content, runtime keys in diagnostics, unnecessary request history, account-linked metrics or observability exports. Native tokens remain separate from the shared accounting key. Initial credentials are created only during explicit init; serve does not upsert/reset them.

Logging remains **unconditionally disabled through the SDK**: supported settings saves/updates force persisted `Logs.MaxDays=0`; runtime stays zero across reload/restart, including after unrestricted SQL/restore changes to metadata. Keep Logs UI/API available but empty in the qualified fresh synthetic state, not forbidden; arbitrary restored historical rows are not scrubbed. AuthAlert's IP/UA-derived login-origin recording and alert mail are disabled through supported collection/model/mailer hooks, including when manual SQL bypasses collection validation; MFA/OTP and other SDK-supported auth controls remain available. Closed typed diagnostics are transient and count propagated failures once; no raw SDK exceptions, URLs/tokens, credentials, private configuration or stacks in HTTP errors, console/stdio or artifacts. Existing closed-category error aggregates remain the only approved native error projection; no new export or success/activity/financial counters.

Auth/preferences/drafts and file-token cache stay page-memory only, including reload logout. The operator explicitly accepts token-bearing URLs **only for manual native backup/protected-file downloads**. Tokens must not be copied into diagnostics/telemetry. Browser/DevTools/download history, password managers, operator files, sensitive snapshot contents, platform/network metadata, WAL/deleted pages and host-native history remain independent persistence/trust boundaries. Snapshot downloads leave the enclave; no automatic upload, log, support bundle or whole-browser/whole-platform transience claim follows. Credential prefill in login URLs stays removed.

Implementation versus remaining UI/build/runtime gaps are recorded in [operator dashboard](docs/operator-dashboard.md). This exception authorizes no installation, inference, telemetry export, new resources, publication or deployment.

## First telemetry scope: metrics only

Use supported Go OpenTelemetry metrics SDK/exporter libraries with explicit, closed observations and a bounded in-memory release policy. Do not copy gateway Rust code or reimplement OTLP. Export directly over authenticated, hostname/certificate-verified OTLP HTTP/protobuf TLS to Honeycomb US; no Collector, agent, external platform reader or log bridge.

Proposed minimal first signals:

- Intake-process CPU cores used and approximate RSS bytes: complete one-minute means of six ten-second numeric samples, following the gateway's cadence. Distinguish process RSS from Go heap and enclave allocation; do not fabricate container/host scope or utilization percentages.
- Custom accounting HTTP terminal counts, coarse status classes and fixed latency-bucket counts: complete non-overlapping five-minute windows. Define one matched terminal population; no per-request export, exact latency sums/min/max, exemplars or trace links. Health, attestation and operator-admin requests are excluded from this initial request family.
- Resource fields limited to fixed `service.name=possums-intake`, an honest deployment environment and an operator-assigned infrastructure slot such as `intake-01`. No automatic host/process/cloud/resource discovery, instance UUIDs or request-derived attributes. No model/payment-provider/endpoint cross-breakdowns in the first pass.

Pin exact metric names, units, bucket boundaries and complete-window/lifecycle/arithmetic checks during implementation. Incomplete, inconsistent or unavailable values are unavailable, not zero or healthy. Carry over the gateway's complete five-minute policy with no minimum-observation or linked-sparsity threshold; do not invent a new suppression framework. Sparse aggregates can describe individual activity and correlate with external timing. This is minimization, not ORAM, anonymity or differential privacy.

## Mandatory interface failure classification and error aggregates

**Operator-approved scope extension:** every project-controlled intake↔PocketBase and intake↔gateway failure boundary must produce a stable, locally authored typed classification. This includes custom accounting HTTP, native operator interactions, background maintenance, initialization and shutdown. Gateway-side changes remain separately deferred; this governs the intake side of that contract. Policy approval is not evidence that complete coverage or new metrics are implemented.

- Classify from supported typed errors, validated protocol/status evidence and the known failing stage, never exception text, SQL, request values, URLs or a parser's offending input. Preserve known classifications across wrappers. Expected refusals and unexpected exceptions must be distinguishable.
- Every caught unexpected exception/panic needs a component/stage-specific fallback with cause explicitly unknown. No bare `failed`, `unknown error`, untyped escape, swallowed exception or raw exception disclosure is acceptable at a project-controlled boundary. This cannot guarantee interception of process termination or failures entirely inside external frameworks; reproduce and document those limits, rather than claim coverage.
- Keep known accounting outcomes authoritative. Classification, cancellation or later presentation/cleanup failure must not invent rollback, successful delivery, settlement or refund, or erase a known committed result. Detailed safe code/stage/constraint/outcome/next-step diagnostics remain transient and separate from telemetry.
- Permit **failure counts only** in a new, explicitly reviewed closed-enum error family: complete, non-overlapping five-minute windows, with only locally fixed error categories as point attributes. The scope includes native operator and background PocketBase failures, not just custom requests. It does not authorize native success/activity counts, financial-mutation counts, operator latency distributions or generic CRUD hooks. Health/attestation are not new request-metrics populations.
- Count each observed boundary failure once at a designated owner; propagation through ledger, native and HTTP wrappers must not count the same failure again. Document ownership, expected refusals, distinct subsequent delivery failures and normal shutdown exclusions. Do not introduce identifier registries or retained per-request failure records to deduplicate.
- Exact metric names, finite categories, mapping and bounded arithmetic/state must be pinned and reviewed before export. No free-form error labels, dynamic SDK/Go type names, raw diagnostic structs or automatic export of all detailed diagnostic codes. No account, amount, endpoint, operation, status, error-message or identifier cross-breakdowns in this family. Apply the final in-process serialization allowlist to actual synthetic wire bytes.
- Complete-window heartbeat, overflow/integrity checks, partial-window loss, sparse-window risk, bounded queue, no retry/spool and shutdown rules remain mandatory. Invalid/incomplete observations mean unavailable, not healthy zeros. Classification is unconditional; collection/export remains conditional. Disabled telemetry, early startup failure, shutdown, process exit and dropped export may prevent a failure reaching Honeycomb. Never weaken the off switch or flush partial windows to promise delivery of every exception.
- Telemetry receives only numeric closed categories after the authoritative operation boundary, outside accounting transactions. It must initiate no accounting, retries, recovery, inference or extra database reads. Exporter failures must not recurse into their own export pipeline.

Acceptance requires a boundary-to-type/owner inventory plus synthetic negative tests of known typed failures, unexpected errors/panics, native framework/authentication failures, background failures, commit/presentation/cleanup races, propagation deduplication, complete sparse/zero windows, disabled/outage/shutdown behavior and hostile values absent from actual serialized metrics, HTTP and stdio. Record unimplemented/unreachable/external limits explicitly. Live export remains separately unauthorized.

## Forbidden collection and defaults

No production logs, access/request records, request-level traces, automatic HTTP/SQL instrumentation, profiling, session replay or trace-to-metrics pipeline. Sampling is not sanitization.

Never put the following into telemetry, exporter diagnostics, logs or support artifacts:

- Account/customer IDs, reservation/idempotency/submission/event/transaction IDs, stable pseudonyms or hashes of identifiers.
- Balances, credit/reservation/settlement/payment amounts, money flows, token/cost events or per-account totals/counts.
- Payment payloads, Stripe customer/payment data, Monero addresses/payment identifiers, wallet or chain records.
- Credentials, superuser tokens, encryption/wallet keys, headers/cookies, URLs/query strings, bodies, client IPs or user agents.
- Exact request timestamps/durations/sizes, SQL text/parameters, raw SDK/parser/database/upstream exceptions, stack traces, panic payloads, environment values or process arguments.

PocketBase's logging/error defaults and built-in admin APIs need actual qualification; being inside an enclave does not permit creating an activity log. Native backup download URLs contain file tokens: the manual-admin exception above permits those first-party download URLs only. Some stock backup error paths contain raw exceptions; the project-controlled diagnostic boundary must still replace them with closed content-free errors. Keep useful closed diagnostics transient and content-free; do not turn them into telemetry labels or automatic bundles.

## Export, retention and failure behavior

Apply a final allowlist in-process before supported SDK serialization/export. Do not rely on vendor-side deletion or unrestricted inherited OTel configuration. Permit only the fixed Honeycomb US endpoint and reviewed ingestion header; credentials are runtime secrets, never metric fields. Refuse redirects. Keep batching/state and transport attempts bounded; no disk spool, unbounded backlog or automatic replay of failed metric batches.

No hot-toggle framework or one-second shutdown guarantee. Drop partial windows and pending batches on restart/shutdown; do not flush incomplete data.

Telemetry outages, sanitizer/SDK errors and disabled export must not change balances, reservation expiry, credits, retries, readiness or settlement outcomes. Never perform export while holding an accounting transaction. Do not detach secret/payload-bearing export work past shutdown. Standard DNS completion/whole-process exit timing remains an external runtime limitation, not a reason to invent a custom resolver.

Honeycomb is outside the enclave boundary. Apply the gateway's provider-default retention acceptance for the MVP, recording the actual destination, key permissions and effective retention when separately verified. Seven days is a future goal, not a current guarantee. Do not assume the gateway's existing key/dataset grants intake access or reuse them without authorization. Restrict operator access; no public boards, secondary archives or support exports. Platform observability and transport/audit retention remain separate unknowns; the off switch disables our exporter, not Tinfoil's collection.

## Temporary synthetic startup diagnostic exception

The operator explicitly authorizes temporary startup observability **only** for isolated disposable `synthetic-serve` with exact `LEDGER_SYNTHETIC_STARTUP_DIAGNOSTICS=true`. This does not authorize ordinary init/serve diagnostics persistence, real-data use, deployment, inference, telemetry, request logging, traces, automatic bundles or broader error capture. The gateway's [forbidden-data rules](../possums/PRIVACY.md#telemetry-permitted-signals-and-forbidden-data), [processor boundaries](../possums/PRIVACY.md#processors-retention-access-and-shutdown) and this document's [forbidden defaults](#forbidden-collection-and-defaults) remain applicable.

One owner-only, replaceable record at fixed container `/tmp/possums-intake-startup/record.json` may contain only schema version, closed startup state/phase and an allowlisted locally authored failure code. Maximum encoded/read size is 512 bytes; directory/file permissions are 0700/0600. No append/history, timestamps, PIDs, paths/addresses, values, credential lengths, identifiers, amounts, raw errors or stacks. Atomic replacement uses at most one private staging entry. This is a narrow runtime-filesystem persistence exception: the latest record (and at most a crash-left staging entry) may survive until container temporary storage is destroyed; it is not secure erasure or a freshness proof. `TMPDIR` cannot select this destination. Same-UID operator compromise and platform/storage retention remain external boundaries.

Before successful listener bind, an observed startup failure may write the closed failure and keep the process alive **at most 120 seconds of diagnostic hold**, solely so Docker can execute its healthcheck. SIGINT/SIGTERM cancels that hold through the original root context. Existing cleanup runs first; this adds no listener, worker, retry, reinitialization or financial action. Success and post-bind failures keep existing joined lifecycle/exit behavior without this hold. Diagnostic filesystem failure cannot change authoritative startup/accounting outcomes or erase the primary stderr failure. Only the opt-in recorder may attempt at most one additional locally authored JSON stderr diagnostic per startup: `SYNTHETIC_STARTUP_RECORD_UNAVAILABLE`, stage `startup_record`, a closed failing constraint, cause explicitly unknown and a private-inspection next step. Its outcome concerns recording only; diagnostic cleanup uncertainty remains explicit. The recorder alone observes the failed recording attempt through the existing typed owner boundary; helpers do not recount propagation. Further record writes stop after the first failure, while internal phase/bind tracking and the hold bound remain unchanged. A distinct stderr-delivery failure is classified without another report or retry. No successful checkpoint logs, raw errors or arbitrary diagnostic fields are permitted. Off/ordinary invocations and the healthcheck never emit this supplementary diagnostic. A record does not establish readiness or safe teardown.

`synthetic-healthcheck` permits one bounded passive fixed-loopback HTTP GET, without proxy, redirect following, retries, arbitrary URL/path options, state creation or telemetry construction. Only exact successful HTTP readiness establishes a healthy exit; record availability cannot veto that evidence. On failure, strict bounded file validation precedes reconstruction of fixed public-safe code/phase/constraint/outcome/next-step output. Missing, hostile or invalid evidence fails closed; neither file nor HTTP bytes are echoed. This projection is suitable for deliberate platform healthcheck capture, not permission to export private startup errors. Tinfoil may retain healthcheck/boot detail independently; native startup-output retrieval, platform access and retention are unqualified. No whole-platform transience or live diagnosis is claimed. Implementation and local evidence are scoped in [synthetic startup](docs/synthetic-startup.md#temporary-startup-healthcheck-diagnostics).

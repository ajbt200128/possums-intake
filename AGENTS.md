# Repository guidance

## Scope

This is a planning-only repository for the Possums external credit ledger MVP. The operator selected Go and PocketBase/SQLite in a separate Tinfoil container with an encrypted persistent volume, replacing the prior Fly/Postgres proposal. One ledger instance; multiple gateways may call it. No payment intake, cryptographic e-cash, Tor, customer browser UI or speculative infrastructure. PocketBase's operator admin UI may be reused after access/privacy qualification. No backups by default; manual migration/admin work is accepted. The same node will eventually host Stripe and Monero payment intake, but payments remain deferred. Brief funding unavailability and delayed new inference admissions during replacement are accepted; one–two minutes is a target, not a guaranteed bound. Choose the published minimum CPU-only Tinfoil enclave: 2 CPUs / 8192 MB, not the unsupported 1 CPU / 2–4 GB request. This is a planning target, not workload/capacity evidence. Do not implement or provision resources without separate authorization.

Follow `PLAN.md`: durable balances, manual credits, short serialized SQLite write transactions with bounded waiting, Stripe-style reserve/credit idempotency, required immutable reservation timeouts, and atomic once-only settlement/refund/expiry. Use PocketBase's supported transaction callback and its transaction-scoped app for all accounting decisions/effects. Store money exactly as canonical decimal text with checked Go uint64 arithmetic, never PocketBase float NumberField. Trust the gateway's amounts; do not duplicate catalog/usage verification. Expiry releases holds and rejects late settlement; possible upstream cost afterward is an accepted tradeoff. Keep minimal bounded deduplication/terminal records with expired-key replay protection. Do not add owner registries/fencing, indefinite manual recovery holds or financial restore procedures in this MVP. Go/PocketBase is the selected stack. Suggest devenv.sh for the local Go development environment, not as an additional production platform. Pin PocketBase and acknowledge its pre-v1 production-critical warning; qualify actual accounting, restart and upgrade behavior.

All custom accounting endpoints, including balance, require one shared runtime admin key; no accounting RBAC or separate operator/gateway permission tiers on these endpoints. Users read their account balance and complete pending reservation rows through the authenticated gateway, which derives account identity from the session. Include defined row fields such as expiration and idempotency key, but never the admin key; no cross-account/global user row lists. See `PLAN.md` for exact snapshot and serialization requirements.

## Existing authority and privacy

Before planning read `README.md` and the sibling gateway's `/Users/mb5/projects/possums/AGENTS.md`, `SPEC.md`, `OVERALL_PLAN.md` and full `PRIVACY.md`. Read the original overall plan from gateway Git history (`7ee4604:OVERALL_PLAN.md`) as historical context only. Current decisions supersede its old browser/buffered/account-number/post-completion-debit and strong privacy claims.

The ledger is a separate workload, not automatically covered by gateway attestation. Target verified gateway-to-ledger transport and customer-key-encrypted storage; these are not implemented/qualified. Encrypted volumes are beta and lack rollback protection. The operator and platform/network metadata remain trust boundaries. The ledger is not trusted with prompts, responses, history or tool payloads. Persistence requires a scoped policy proposal: necessary accounting is not telemetry, but unnecessary per-request history remains prohibited. Do not export account-linked metrics, request logs/traces, raw errors, credentials or private configuration. Discuss provider logs, database defaults, backup/WAL retention and operator access honestly, without claiming unverified platform behavior. Minimal OpenTelemetry/Honeycomb aggregate metrics are requested under this repository's `PRIVACY.md`: supported Go metrics SDK/exporter, closed fields, complete five-minute request aggregates and complete one-minute process CPU/RSS means, direct authenticated Honeycomb US TLS, no Collector/logs/traces or account/payment IDs/amounts. `OTEL_SDK_DISABLED=true` is the off switch; telemetry failures never affect accounting. Read local and gateway privacy policies before telemetry work and link their applicable sections and synthetic wire/runtime evidence. Place explicit final-outcome middleware only on custom accounting routes and independent process/lifecycle sampling hooks; no generic CRUD/financial-mutation counter hooks. The operator additionally requires stable typed classification at every project-controlled intake↔PocketBase and intake↔gateway failure boundary, including native/operator/background paths, and permits complete five-minute closed-category failure counts under `PRIVACY.md`'s interface-failure extension. Unexpected exceptions require a stage-specific cause-unknown fallback; preserve known accounting outcomes and count a propagated failure only once. Classification remains required with metrics disabled; no guarantee of per-exception export. Pin/review categories, ownership and synthetic wire/negative tests before claiming implementation. Error-only native/background counts do not authorize native activity/success/financial counters or generic CRUD hooks. No generic diagnostic framework, automatic resource discovery, SDK tracing, dashboard/alert expansion or production export is authorized. Review/disable PocketBase request logging and unsafe raw-error paths before real data. Native superuser authentication is an operator control-plane decision distinct from the shared accounting key; do not add customer accounts or a role framework. Stock backup downloads put a file token in the URL: do not expose them unchanged. Optional manual snapshots leave the enclave with sensitive state and do not establish safe financial restore.

New client/gateway attestation-checking work is deferred for this packet. Prefer the platform's existing public evidence surface over a custom verifier/protocol; exposing boot evidence is not fresh/verified evidence. Do not skip required customer-controlled disk-key verification or treat exposure as passing the eventual real-data integration gate. Fresh-attestation socket features remain optional/deferred.

Persistent-volume ledger updates require Tinfoil replacement with downtime, not the gateway's blue-green wrapper. Preserve the original disk/key and qualify bounded gateway reservation/settlement waits before integration. No prompt before confirmed reservation; no automatic inference replay or invented accounting success. Waiting does not extend hold expiry. Avoid simultaneous gateway replacement because pending settlement state is memory-only. Never run two copied ledgers as independent spendable authorities, restore an old database as routine code rollback, or silently initialize empty production state after storage/key loss.

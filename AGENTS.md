# Repository guidance

## Scope

This repository contains planning and the separately authorized standalone local implementation of the Possums external credit ledger MVP. The operator selected Go and PocketBase/SQLite in a separate Tinfoil container with an encrypted persistent volume, replacing the prior Fly/Postgres proposal. One ledger instance; multiple gateways may call it. No payment intake, cryptographic e-cash, Tor, customer browser UI or speculative infrastructure. PocketBase's operator admin UI may be reused after access/privacy qualification. No backups by default; manual migration/admin work is accepted. The same node will eventually host Stripe and Monero payment intake, but payments remain deferred. Brief funding unavailability and delayed new inference admissions during replacement are accepted; one–two minutes is a target, not a guaranteed bound. Choose the published minimum CPU-only Tinfoil enclave: 2 CPUs / 8192 MB, not the unsupported 1 CPU / 2–4 GB request. This is a planning target, not workload/capacity evidence. Do not implement or provision resources without separate authorization.

Follow `PLAN.md`: durable balances, manual credits, short serialized SQLite write transactions with bounded waiting, Stripe-style reserve/credit idempotency, required immutable reservation timeouts, and atomic once-only settlement/refund/expiry. Use PocketBase's supported transaction callback and its transaction-scoped app for all accounting decisions/effects. Store money exactly as canonical decimal text with checked Go uint64 arithmetic, never PocketBase float NumberField. Trust the gateway's amounts; do not duplicate catalog/usage verification. Expiry releases holds and rejects late settlement; possible upstream cost afterward is an accepted tradeoff. Keep minimal bounded deduplication/terminal records with expired-key replay protection. Do not add owner registries/fencing, indefinite manual recovery holds or financial restore procedures in this MVP. Go/PocketBase is the selected stack. Suggest devenv.sh for the local Go development environment, not as an additional production platform. Pin PocketBase and acknowledge its pre-v1 production-critical warning; qualify actual accounting, restart and upgrade behavior.

All custom accounting endpoints, including balance, require one shared runtime admin key; no accounting RBAC or separate operator/gateway permission tiers on these endpoints. Users read their account balance and complete pending reservation rows through the authenticated gateway, which derives account identity from the session. Include defined row fields such as expiration and idempotency key, but never the admin key; no cross-account/global user row lists. See `PLAN.md` for exact snapshot and serialization requirements.

Manual token-bearing downloads introduce browser/history/operator and sensitive snapshot persistence boundaries; never copy tokens/URLs or raw exceptions into diagnostics or observability. Admin-vault/customer-admin records are first-party application data, not permission to retain diagnostic secrets or inference content.

This policy authorizes this focused local source/test/document packet only, not real data, production/integration, gateway edits, new persistence/resources, scheduled/external backups, inference, telemetry export, publication, deployment, commits or pushes.

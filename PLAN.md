### Dependency and storage design

Pin **`github.com/pocketbase/pocketbase v0.40.5`**, a published non-prerelease observed in the [release API](https://api.github.com/repos/pocketbase/pocketbase/releases/latest) and [tagged release](https://github.com/pocketbase/pocketbase/releases/tag/v0.40.5). Its [go.mod](https://github.com/pocketbase/pocketbase/blob/v0.40.5/go.mod) requires **Go 1.27**, `dbx v1.12.0` and `modernc.org/sqlite v1.60.1`; lock the actual toolchain and module checksums during setup. This is upstream-source evidence, not an installed build, long-term support promise or accounting qualification. PocketBase still [warns against production-critical use before v1](https://pocketbase.io/docs/) unless manual changelog/migration work is accepted.

Use versioned **Go migrations and four ordinary SQLite tables in PocketBase's data database**, accessed with supported parameterized `txApp.DB()` queries. This avoids Record hooks, float fields, generated per-record metadata, generic CRUD exposure and accidental after-commit hook failures in the money path. These are not PocketBase collections: the stock dashboard does not become an accounting browser/editor. Do not build one for this MVP. PocketBase native superusers remain a separate full-authority maintenance control plane.

| Table | Defined fields and constraints |
| --- | --- |
| `ledger_accounts` | `account_id TEXT PRIMARY KEY`, `balance TEXT NOT NULL`, `enabled INTEGER NOT NULL` constrained to 0/1. Provision with balance `"0"`, enabled true. No completion counter until a later gateway contract actually requires it. |
| `ledger_reservations` | `reservation_id TEXT PRIMARY KEY`, `idempotency_key TEXT NOT NULL UNIQUE`, `account_id TEXT NOT NULL` foreign key, `maximum TEXT NOT NULL`, `timeout_seconds INTEGER NOT NULL`, `expires_at INTEGER NOT NULL`, `state TEXT NOT NULL` constrained to `active/settled/refunded/expired`, `charged_amount TEXT NULL`, `terminal_at INTEGER NULL`, `retain_until INTEGER NULL`. Active terminal fields are null; terminal charged amount is canonical text (`"0"` for refund/expiry). Original inputs/expiry never change. |
| `ledger_credits` | `idempotency_key TEXT PRIMARY KEY`, `account_id TEXT NOT NULL` foreign key, `amount TEXT NOT NULL`, `balance_after TEXT NOT NULL`, `committed_at INTEGER NOT NULL`, `retain_until INTEGER NOT NULL`. `balance_after` is the original credit result, not a later current balance. |
| `ledger_meta` | One fixed singleton row with `schema_version INTEGER NOT NULL` and `clock_high_water_ms INTEGER NOT NULL`; no request/account identifiers. Missing row is invalid state, not an invitation to reset. |

Indexes beyond primary/unique keys: reservations `(account_id, state, expires_at)` for availability/snapshots; `(state, expires_at)` for expiry; partial `(retain_until)` for terminal pruning; credits `(retain_until)`. Foreign keys prohibit orphan records and account deletion while referenced. No account delete/reset API. Migrations add structural state/null/range checks; Go validates every stored amount and uses checked arithmetic, never SQL `SUM`, casts or arithmetic over money text. Corrupt/unknown schema or impossible balances fail closed, not “repair” by deleting holds.

Set WAL, `synchronous=FULL`, foreign keys on, `busy_timeout=250` milliseconds and memory temp storage on **each connection** through PocketBase's supported `DBConnect` configuration. Retain other safe upstream connection options. The [tagged defaults](https://github.com/pocketbase/pocketbase/blob/v0.40.5/core/db_connect.go) instead use `NORMAL` and a 10-second busy timeout; defaults are not this durability/budget contract. Verify effective pragmas and restart/acknowledged-write behavior. WAL/deleted pages are retained storage, not secure-erasure evidence; filesystem/platform durability still needs later qualification.

### Wire schema and endpoints

Listen on loopback for local acceptance. All accounting routes are POST with JSON media type (standard parameters such as `charset=utf-8` accepted), one object, **4 KiB maximum body**, no compression, duplicate keys, trailing JSON, null required fields or query parameters. Ignore extra JSON fields for additive compatibility; never bind, persist, echo or export them. Known required fields retain exact names/types; money/timeout semantics are checked by the ledger core, not duplicated by HTTP handlers. Bound headers to 8 KiB. Account IDs match the gateway's opaque valid UTF-8, 1–128 byte identity contract, including escaped controls; no normalization, trimming, extra character-class ban or conversion to a PocketBase record ID. Reservation IDs are server-generated 128-bit cryptographic random values encoded as 32 lowercase hex characters; collision fails/retries before commit, never overwrites a row.

Money on the wire and disk is a string matching `^(0|[1-9][0-9]{0,19})$`, then checked against `18446744073709551615`. Credit and maximum must be positive; settlement may be zero and must not exceed its maximum. `timeout_seconds` is a JSON integer in **1–1800**, required on every new reserve. Caller recommendation: **600 seconds**; the server supplies no omitted default. Retry must repeat the original timeout. Time fields use signed SQLite epoch milliseconds internally (not float); responses use fixed UTC **`YYYY-MM-DDTHH:mm:ss.SSSZ`**, null where specified. No caller-supplied reservation expiration date.

| Path | Required request fields (extras ignored) | Successful response |
| --- | --- | --- |
| `/accounts/provision` | `account_id` | `{account_balance:[account row]}`; repeated ID returns existing row, never resets balance/enabled state. |
| `/credits` | `account_id`, `amount`; required `Idempotency-Key` | `{credit:credit row}`; repeats return the original committed row. |
| `/reservations` | `account_id`, `maximum`, `timeout_seconds`; required `Idempotency-Key` | `{reservation:reservation row}` including any retained terminal state on retry. |
| `/reservations/settle` | `reservation_id`, `charged_amount` | `{reservation:reservation row}` with the first committed terminal outcome. |
| `/reservations/refund` | `reservation_id` | Same terminal-outcome shape. |
| `/reservations/lookup` | `reservation_id` | `{reservation:reservation row}` if retained; never create a hold. |
| `/balance` | `account_id` | `{account_balance:[account row],pending_reservations:[reservation rows],available:"…"}` from one transaction/snapshot. |

Successful operations return HTTP 200, including exact retries. Account JSON fields are exactly `account_id`, `balance`, `enabled` (boolean); reservation/credit JSON fields are exactly their table fields above, with time conversion and nulls specified above. `ledger_meta` is never returned. Balance returns all active, unexpired rows for that account ordered by reservation ID, not terminal or credit history. No silent truncation, generic table dump or future-field auto-export; inability to produce the complete snapshot is an explicit availability error, not a partial success.

`GET /healthz` is the only required public route and returns fixed cached readiness, with no details, identifiers or accounting work. It is ready only after existing-state validation, migration and usable storage; observed fatal storage failure clears readiness. No custom attestation route unless the platform evidence surface actually proves insufficient later.

Use a runtime-injected high-entropy admin key (at least 32 random bytes), `Authorization: Bearer`, constant-time comparison; never return it, place it in URLs/images/files/logs or accept redirects. Provision, credit, reserve, settle, refund, lookup and balance all use the same authority. Users later see balance only through their authenticated gateway session, which derives the account ID; no client-selected cross-account/global lists or client possession of this key. The local synthetic caller proves ledger scoping, not the unchanged gateway's user isolation.

Errors use a small closed typed response `{code,stage,constraint,outcome,next_step}`, with locally authored text/enums, never offending values or raw SQL/SDK/parser/panic text. Pin codes/tests with the handlers: 400 invalid schema/key, 401 missing/wrong key, 404 unknown account, 409 insufficient credit/disabled admission/key-input conflict/expired settlement, 410 reservation evidence unavailable, 503 writer/storage unavailability or unknown commit outcome. Known rolled-back/no-effect and unknown outcomes must differ. For 410, absence is **not** proof a reservation never existed or was refunded. A late settlement returns 409 and, while retained, its authoritative expired reservation separately from the content-free diagnostic. Other duplicate/conflicting terminal attempts return the first committed row without changing money; callers must inspect its state, not equate HTTP 200 with their requested effect. Response loss is never a receipt. Retrying the same identity may resolve uncertainty; a new key can create another effect.

Mandatory interface failure classification covers every project-controlled intake↔PocketBase and intake↔gateway boundary, including native operator, initialization, maintenance and shutdown. Preserve supported typed categories and authoritative outcomes; unexpected exceptions require stage-specific, cause-unknown typed fallbacks, never raw exception text or silently discarded failures. The operator permits complete five-minute closed-category failure counts for all these interfaces under [the scoped privacy extension](PRIVACY.md#mandatory-interface-failure-classification-and-error-aggregates). Classification is mandatory even with telemetry disabled; metrics are not guaranteed delivery of every exception. Exact inventory, category mappings, once-only observation ownership and negative tests are required before claiming coverage. No gateway code changes or generic diagnostic framework follow from this policy.

Additive tolerance does not imply compatibility with changed field meanings, units, required fields or replay semantics. There is currently no external-ledger adapter in gateway main: its memory-only `Accounting` uses u64 microunits and 32-byte submission IDs, not this service's HTTP DTOs or timestamped reserve/credit keys. A future separately authorized adapter must map identities/envelopes/keys, validate authoritative terminal receipts and preserve unknown outcomes; changing the gateway's own strict API parser is not authorized here. See [compatibility pass](docs/gateway-compatibility.md).

### Writer, time and immutable key validity

Use one context-aware in-process writer gate for **all** accounting operations, including balance/lookup expiry and cleanup. Wait at most **2 seconds** (or the shorter caller cancellation); do not reject just because a fast writer is occupied. After acquisition use PocketBase's supported `app.RunInTransaction(func(txApp core.App) error)`; **every accounting read, clock/key decision and effect uses that `txApp`**, never the outer app or separate Record API calls. No network, exporter or inference work inside it. The [tagged implementation](https://github.com/pocketbase/pocketbase/blob/v0.40.5/core/db_tx.go) uses the single-connection nonconcurrent writer and binds both transaction DB builders to the same transaction.

Local HTTP budgets: read header **2 s**, whole body read **5 s**, write **5 s**, idle **30 s**; synthetic caller total RPC deadline **5 s**, with no automatic mutation retry. After acquiring the gate, queries share a **1 s transaction-work context**, checked before commit; configure PocketBase query timeout to **1 s** as well. Cleanup uses the same gate/budgets. Do not mutate a shared DB handle's context or spawn an abandoned goroutine that may commit after a reported “no effect.” `RunInTransaction` has no context parameter and OS commit/fsync is not a hard real-time bound: qualify cancellation, external SQLite locks and begin/commit stalls against this version. On uncertain commit/delivery return unknown, retain gate ownership until actual completion, and never invent rollback. Exceeding the RPC budget cannot extend expiry. Later gateway replacement waits are a separate integration policy, not hidden 120-second server transactions.

Inside each transaction, obtain UTC epoch milliseconds from SQLite and set **`now = max(database_time, persisted clock_high_water_ms)`**. Advance that singleton in the same committed transaction as pruning/effects; use this effective DB time for key checks and deadlines. This tiny durable watermark prevents clock rollback after pruning from reopening a key window; it is not a lease, owner registry or protection against restoring an old disk. A forward clock jump may expire holds early; after a backward jump the effective clock can remain ahead until wall time catches up. Never reset the watermark to repair time. Test these cases and disclose this local-clock limitation before real data.

Idempotency keys are exactly **`v1.<13 decimal epoch-millisecond digits>.<32 lowercase hex random digits>`** (49 ASCII characters). Timestamp and nonce are caller-generated once and immutable across retries. Scope uniqueness to operation (`reserve` versus `credit`), globally across accounts within that operation; another account/body with the same scoped key conflicts. Reject malformed/duplicate headers. A timestamp alone is not authorization or evidence of a previous effect.

1. After syntax validation, resolve a retained scoped key first. Compare all original typed inputs: account + maximum + timeout for reserve, account + amount for credit. Mismatches return 409. For a matching reservation, apply its due expiry in the same transaction **before** returning its current row; never return a past-deadline hold as active. Matching retries return that row/original credit result even after key validity ends. Retrying reserve never resets expiration.
2. With **no retained row**, a new effect is allowed only when **`issued_ms <= now + 60,000` and `now < issued_ms + 86,400,000`**. Use checked timestamp arithmetic. Too-far-future and expired keys reject without effect. Exact expiry is rejected. Renewing the timestamp/nonce is a new identity, never a safe retry of an unknown effect.
3. Retain active reservations through terminal transition. Retain terminal reservations until **`max(issued_ms + 24 h, terminal_at + 24 h)`**, and credit markers until **`max(issued_ms + 24 h, committed_at + 24 h)`**. Expiry's terminal time is the original deadline, not the later cleanup time. At `now >= retain_until`, pruning is allowed. Thus a missing/pruned key is already ineligible for a fresh effect; a future-skewed key cannot outlive its marker. Keep the small v1 parser/rejection rule across future key versions; unknown versions reject.
4. Failed validation, insufficient credit and rolled-back transactions create no successful-effect marker and may be retried under the same still-valid identity. An absent reservation lookup returns evidence unavailable, never a fabricated result. Only successful accounting effects need bounded recovery rows; no permanent UUID tombstone collection.

Required replay tests: boundary milliseconds, 60-second future skew, backdated keys, altered inputs/timestamp, cross-account conflict and operation scoping, lost response, active/terminal retry, exact prune boundary, future-skew retention, restart, backward clock after committed pruning, and forward-clock expiry. Prove a previously effective key cannot become a fresh reserve/credit after its marker is deleted. This proof depends on retaining the original database/watermark, not on trusting a reusable UUID or claiming disk rollback resistance.

## Accounting transaction rules

**Available = total unspent balance − active holds.** Reserve does not debit the total; settle deducts its final amount; refund/expiry release capacity without debiting. Every committed balance/hold sum/difference must fit `uint64` and remain nonnegative. Account disabled state blocks new reservations, not closure of existing holds or scoped reads.

- **Provision/credit:** provision is idempotent on account ID and never resets it. Credit requires an existing account; resolve its scoped key, checked-add the amount and insert the original result marker in the same transaction. Overflow rolls everything back.
- **Reserve:** resolve its key first, expire due holds affecting that account through the ordinary transition, then require an enabled account and sufficient available credit. Set `expires_at = now + timeout_seconds × 1000` once. Genuine insufficient credit does not wait for an inference to finish. Unique keys and the serialized transaction protect creation.
- **Settle/refund:** load the reservation/account, expire it if `expires_at <= now`, otherwise terminalize it once and apply any debit atomically. Settlement is at most its maximum. Existing terminal state wins every race, including a conflicting final amount or later refund. No deletion-as-expiry and no separate balance updates.
- **Balance/lookup:** use the same transaction/time/expiry path before returning evidence; balance and all pending rows come from one consistent snapshot. Admission cannot ignore a hold as expired while settlement can still charge it.
- **Cleanup:** one in-process tick every **10 s** expires at most **128 due rows** per transaction; every **60 s** prune at most **128 eligible terminal/credit rows** per transaction. Repeat on later ticks, not an unbounded writer loop. Account admission/read correctness never depends on cleanup keeping up; delayed pruning only retains evidence longer. No external job queue or recovery service. Measure local backlog/transaction behavior without exporting account-linked counters.

## Schema and service contract

Fresh explicit `init` creates the **first unreleased schema v1**. Transaction-scoped `core.NewBaseCollection` / `SaveWithContext` creates `ledger_accounts` metadata and its generated table. Initialization verifies that the table did not previously exist and is empty, then replaces **only that new empty table in the same transaction** with versioned constrained DDL. No `UnsafeWithoutHooks` registration of an existing SQL table.

- Fixed collection name `ledger_accounts`, collection ID `ledgeraccounts1`; a separate internal 15-character native record ID is the primary key. External `account_id` remains unique and is still the reservation/credit foreign-key target. No duplicated balances, account timestamps or relations. Reservations, credits and metadata remain ordinary SQL tables.
- Required native TEXT `account_id` (max 128 characters) additionally obeys existing 1–128 **byte**, valid UTF-8 validation (opaque identities, no normalization; the compatibility pass removed the extra control-character ban). Required TEXT `balance` has max 20 characters and canonical decimal pattern, followed by full `ParseMoney` uint64 validation. SQL preserves canonical TEXT and uint64-max checks. `enabled` is Bool **without Required**, so false remains valid. Collection API rules are nil.
- `schemaV1` / `migrateV1` define fresh initialization, with `schema_version=1`. There is no v1→v2 migrator or version-specific legacy preflight. `Open` reuses exact nine-DDL/index checks in a read-only layout guard before framework bootstrap, then validates native collection fields/indexes/type/identity/rules, pragmas, integrity, relationships and accounting consistency.
- Earlier **old-layout disposable databases can also say v1**; that number never substitutes for strict DDL/collection-metadata validation. They are refused, not silently reset/migrated/rebuilt. Explicitly select a **new empty disposable directory** for `init`; reusing a test directory requires separately and deliberately discarding only its disposable contents before init. Never use this as storage/key-loss recovery. There is no previously released ledger schema to upgrade. Missing/partial storage refusal is unchanged.

`Provision` now uses `core.NewRecord` and transaction-scoped `SaveWithContext`, with three bounded cryptographic internal-ID collision checks. Existing external account/API response shapes and idempotency semantics are unchanged. Credit/settlement scoped SQL remains supported.

`Service.NativeAccountCreate(context.Context, NativeAccountCreate) ([]byte, error)` and `Service.NativeAccountUpdate(context.Context, internalID, NativeAccountPatch) ([]byte, error)` use the same `s.run` writer gate, work/cancellation budgets and durable clock watermark as accounting. Updates discard stock-controller loaded state and fetch fresh state inside the transaction. Internal/external identity is immutable; changed absolute balances reject with `LEDGER_NATIVE_BALANCE_HELD` while active holds remain. Due holds expire through the ordinary accounting path; enabled changes are permitted. Saves all use the transaction-scoped app. An account-only `OnRecordValidate` hook checks money/identity, not metrics/logging.

Native RecordJSON is bounded/pre-encoded inside the callback and published **only after observed commit**. Unknown commit returns no requested success bytes; known commit survives later hook/presentation errors or panics. Interrupted postcommit HTTP delivery aborts without resubmission or invented rollback. **Absolute fake-balance edits are synthetic operator actions, not production funding or credit-idempotency receipts.** Native reads are stored totals, **not available-balance snapshots**; use authenticated custom `/balance` for the latter.

## Restricted native surface

- `init --operator --state <absolute-empty-directory>` reads runtime-only operator email/password, validates them before filesystem effects and creates exactly one password-only native superuser in the initialization transaction. No argv credentials, automatic serve/upsert/reset, installer or recovery route. Auth-alert origin persistence, OTP/MFA/OAuth are disabled and refused by operator-mode qualification if re-enabled.
- `serve --operator` shares the existing app via `operator.NewHandler(accounting, app, service)`. Numeric loopback policy, explicit state, normal lifecycle and default non-operator exclusions remain unchanged.
- Native superuser authentication is **distinct** from the custom shared accounting key. Native tokens never authorize custom accounting; the server never injects that key into requests or browser assets. No roles/customer accounts or new permission tiers.
- Native authentication plus authenticated collection list/scaffolds/provider/settings reads remain available. Account metadata and record routes permit only the fixed initialized account collection name/ID. Named `_superusers` reads remain available; arbitrary collection aliases/other internal data are denied.
- Only account-record POST/create and PATCH/update are permitted. Strict bounded JSON parsing runs before PB request binding, modifier replacement or TextField coercion. It rejects duplicate/unknown/modifier keys, numeric/null balances, wrong account/bool types, invalid UTF-8, unpaired surrogates, compression, trailing data and incorrect collection envelope values. Create allows the native editor's empty ID; update checks any supplied ID against fresh state.
- Account create/update hooks stop the stock submit finalizer and call the Service methods; **no `e.Next()` into another financial writer**. Native-compatible responses retain closed diagnostics, outcome and HTTP status.
- DELETE, other record writes, collection/settings mutations, backups/download tokens, logs, files, batch, realtime, SQL and recovery/install APIs remain denied. Canonical paths/queries and single authorization values are enforced before the mux can redirect.

Actual SDK/browser qualification found these required reads: exact SDK 0.28.1 auth-methods projection `fields=mfa%2Cotp%2Cpassword%2Coauth2`; collection-list `page=1&perPage=1000&skipTotal=1`; record-list pagination/empty filter and native default `sort=-%40rowid`; total-count `fields=id`; native account collection-ID detail paths. The 1000-page-size exception is metadata-only. Unknown/duplicate/encoded-key/redundant-encoding/query aliases fail closed; fields/sorts are closed local read selectors, not a copied frontend schema.

## Logging stays off

PocketBase logs are disabled by default in both the normal custom-accounting service and opt-in native operator mode. `initializeFramework` sets `Logs.MaxDays=0` before bootstrap and overrides it on settings reload; the native router's activity logger stays unbound. Native auth-alert origin persistence remains disabled. Authenticated operators cannot read `/api/logs` or `/api/logs/stats`, nor change settings; the normal service exposes none of those native routes.

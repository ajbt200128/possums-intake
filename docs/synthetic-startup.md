# Disposable synthetic startup

**Subsequent local website extension:** current source also initializes the
website/customer-auth schema and initial code in this fresh disposable mode,
without seeding customer keys or credit. Website setup has its own closed
`website_setup` checkpoint and cause-unknown fallback. Session cleanup follows
the separately accepted stock process-lifetime policy; it is not a joined
in-process worker. See [default website runtime](website-runtime.md). Historical
image/platform evidence below does not qualify this website extension.

`intake synthetic-serve` is an explicit standalone native-dashboard test mode. It defaults to `0.0.0.0:8090` for container reachability. The only option is `--listen`: a numeric loopback or wildcard IP and canonical decimal port (including `0` for OS selection). Hostnames, interface zones and other interface addresses are rejected. Port zero is not advertised; choose a known port for interactive use.

`--state` is rejected even when empty. `--operator` is also rejected, including `--operator=false`: synthetic mode always selects the restricted native operator surface. Credentials cannot be CLI options. Unknown commands/options or positional arguments fail closed.

Inject throwaway runtime `LEDGER_ADMIN_KEY` (at least 32 bytes), `LEDGER_OPERATOR_EMAIL` and `LEDGER_OPERATOR_PASSWORD` (valid email; valid UTF-8 password of at least eight characters and at most 71 bytes). They are validated, along with the listener, before scratch creation. Never use real credentials or accounts. No setup URL, credential, state path or success banner is printed.

Each invocation uses `os.MkdirTemp` under the standard runtime temporary directory (`TMPDIR`, ordinarily `/tmp` in the container). It explicitly initializes new empty state and one native operator with the supported `InitOperator` transaction path, then opens that same state. It does not reuse, reset or select persistent state, and never grants seed credit. Native operator tokens cannot authorize custom accounting routes; those still require the shared accounting key. The accounting key cannot authorize native operator routes.

Synthetic startup never constructs the telemetry runtime/exporter, regardless of inherited Honeycomb or generic OTel configuration, and does not mutate the process environment. Request/activity logging remains disabled through the existing restricted service and operator handlers. See [intake forbidden collection](../PRIVACY.md#forbidden-collection-and-defaults), [export behavior](../PRIVACY.md#export-retention-and-failure-behavior) and [gateway telemetry policy](../../possums/PRIVACY.md#telemetry-permitted-signals-and-forbidden-data). This says nothing about platform logging or native agent-host history.

SIGINT/SIGTERM uses the existing joined HTTP/maintenance shutdown, then storage close. Only confirmed safe teardown allows recursive removal of this invocation's scratch directory. Init/open failures, lifecycle panics or unconfirmed shutdown/close preserve scratch state for private runtime inspection; it must not become reusable ledger state. Removal failure reports a closed cleanup diagnostic with unknown removal outcome. Earlier observed failures retain diagnostic precedence. No worker is detached or retried for cleanup. Process crash/forced kill and runtime storage destruction are not graceful-cleanup evidence. TMPDIR permissions, tmpfs sizing and container runtime configuration remain operator/parent-owned.

Ordinary `init` and `serve` defaults remain unchanged: explicit absolute state, no automatic initialization by serve, numeric loopback-only serving, and separately explicit `--operator` opt-in.

## Temporary startup healthcheck diagnostics

This is an explicitly authorized, isolated synthetic-only diagnostic packet under the [narrow privacy addendum](../PRIVACY.md#temporary-synthetic-startup-diagnostic-exception). Activate only by passing `synthetic-serve` as the first argument **and** injecting exact `LEDGER_SYNTHETIC_STARTUP_DIAGNOSTICS=true`. Other spellings, diagnostic-off synthetic invocations and ordinary `init`/`serve` keep their previous behavior. No deploy config or activation is included here.

The small startup recorder checkpoints `validation`, `scratch_create`, `initialize` (around `InitOperatorObserved`), `open` (around `OpenObserved`), `operator_handler`, `website_setup` and `listener_bind`. It writes one canonical record at fixed `/tmp/possums-intake-startup/record.json`; `TMPDIR` still controls scratch state but never diagnostics. The private directory is 0700 and replacement file 0600; a single private `next` staging entry is renamed atomically. No appends or history. Only version, fixed `starting`/`failed`/`bound` state, fixed phase and closed code are allowed; the whole record is limited to 512 bytes. No timestamps, IDs, paths/addresses, configuration values, credential lengths, raw errors or stacks enter it. Typed project diagnostic codes are projected through a phase-specific local catalog; unexpected causes get a phase-specific `SYNTHETIC_*_CAUSE_UNKNOWN`, without exception-string parsing. File failures cannot replace authoritative startup/accounting outcomes or the existing main stderr diagnostic. The writer returns a closed stage-specific `RuntimeSetupUnknown` diagnostic; only the opt-in recorder observes that attempt once and attempts one supplementary JSON stderr line (`SYNTHETIC_STARTUP_RECORD_UNAVAILABLE`, `startup_record`, closed constraint, diagnostic-only recording outcome, explicit cause unknown and private-inspection action). Any diagnostic cleanup uncertainty remains explicit while the first recording constraint is preserved. It reconstructs local templates rather than serializing arbitrary helper fields. After the first recording failure it stops all further record attempts, still tracking phase/bind state internally. A distinct supplementary stderr-delivery failure is classified as `ResponseDeliveryUnknown`, observed once, and never retried or recursively reported. No successful checkpoint logs are added.

On pre-bind startup failure, existing joined teardown/scratch rules run first, then the failure record is attempted only if recording has not already failed, and the process waits at most 120 seconds solely for healthcheck capture. It starts no listener/worker, retries nothing and reinitializes nothing during that wait. SIGINT/SIGTERM immediately cancels the added wait through the original root context. There is no duration environment variable or CLI option. A successful bind records `bound`, **not healthy**; success and all post-bind failures retain existing joined exit behavior, with no added hold. The hold bounds only the extra wait, not preexisting initialization or joined teardown. Init/open uncertainty still preserves scratch state; safe bind-failure cleanup still removes it. Earlier primary failures retain precedence over cleanup or diagnostic-filesystem failures.

Use exact command `intake synthetic-healthcheck` with **no options** for a container exec healthcheck. It performs one passive GET to fixed `http://127.0.0.1:8090/healthz`, with proxy disabled, redirects refused, keepalive reuse/compression disabled, 4096-byte response-header bound, 65-byte body read bound and a two-second total HTTP deadline. Only HTTP 200 with exact `{"status":"ok"}` (optional final newline) returns zero; no startup record can establish health. This command constructs no ledger, telemetry runtime, scratch state or diagnostic record and never retries or mutates anything. A custom synthetic `--listen` port must not be paired with this fixed-port healthcheck.

When HTTP readiness is unavailable, the command opens the fixed private directory/file without following descendant symlinks, refuses unsafe types/permissions/owners/hardlinks and bounds reading before strict canonical schema/enum validation. Unknown/duplicate/case-aliased fields, trailing data and hostile or oversized bytes fail closed. It prints only locally reconstructed JSON code/stage (fixed phase)/constraint/`not_ready` outcome/next-step on stderr, never HTTP or file bytes. For example, missing runtime key reports `LEDGER_RUNTIME_KEY_INVALID` at `validation`; a missing/invalid record reports `SYNTHETIC_HEALTH_EVIDENCE_UNAVAILABLE` at `healthcheck`. Healthy HTTP readiness still succeeds when recording is unavailable. A valid record reports the last checkpoint only: it is neither fresh attestation nor a proof of current cause, financial outcome or safe teardown. The container's temporary-storage lifecycle controls residual-record retention; a crash may leave the latest record and one staging entry. This does not qualify platform collection, access or retention.

The parent's local reproduction of the preceding deployed image passed valid startup/UI/auth, bridge-IP, restart and privacy fixtures, while missing/invalid synthetic credentials exited before listener bind; the **remote cause remains unknown**. The supplied Tinfoil CVM v0.14.7 `runContainer` behavior uses an unhealthy configured healthcheck's last output as boot-stage detail; without a healthcheck, successful ContainerStart is marked OK. Dead containers cannot run healthchecks, motivating the bounded opt-in hold. These are parent-supplied context, not a live platform test of this patch. Native startup output retrieval and platform retention remain unqualified. No public deploy repository/config was changed and nothing was deployed, published or enabled by this packet.

# Lisp-native first-party top-up UI

## Authority and scope

The operator approved replacing the temporary standalone Go top-up HTML with this site's existing Lisp UI library and text-buffer visual style, adding an account-page entry, clear status presentation and exact USD summaries. This is local source/tests, not deployment, publication, real sales, gateway integration or permission to replay a payment. The currently running paid synthetic sandbox state must remain untouched by presentation qualification; browser fixtures may use isolated fake providers/accounts.

Read [sandbox evidence](stripe-sandbox-local.md), [top-up contract](stripe-topup-plan.md), and [privacy policy](../PRIVACY.md#subsequent-local-stripe-sandbox-authorization). Preserve server-side authority, once-only creation/funding, privacy, closed diagnostics and known outcomes. `PLAN.md` remains unchanged.

## Implementation contract

- **Lisp owns presentation:** page composition, heading/copy, status wording and whitespace using the existing shared `page` helper, typography, color variables, generated stylesheet and vendored fonts. No additional CSS framework, CDN, script or remote font is needed.
- **Go owns effects:** authenticated account binding, credential checks, CSRF, revision/form-age/attempt guards, fixed denominations, idempotency, Checkout URL validation and authoritative outcomes. The four buttons remain one narrow host-owned form, analogous to the existing host login form. Lisp chooses where the form appears, never its financial authority or secrets.
- Add only inert, bounded, allowlisted host-presentation slots to the pure `pkg/lispsite` node model. The library does not import intake, execute callbacks, start payments, know provider URLs or expose services. Unknown slots fail closed. Reserved `/topup` and `/payments` routes remain Go-owned, not redeclarable Lisp routes.
- A trusted page receives only bounded copied state strings, not API keys, customer credentials, payment/account mapping references, hosted URLs, SDK payloads, balances as mutable objects, or executable capabilities. Form secrets/attempt values are bound only by the Go renderer after Lisp evaluation.
- Top-up GET may present a purchase form; status/return/account rendering cannot enable it. The amount-selection page has the four fixed buttons, not a redundant Add credit self-link. Show **Check payment status** only for pending/uncertain outcomes, not as generic form/confirmed-receipt navigation. It observes webhook-confirmed local funding; a status read never creates, retrieves or confirms a provider payment. Success text must distinguish original funding from current available credit. Unknown/create-only/blocked/unlinked states remain explicit; a failure never advises blind retry.
- Main account summaries display exact USD values with integer arithmetic: `5000000` microunits displays `$5.00`. Preserve up to six fractional digits for sub-cent balances instead of rounding away spendable credit. Following the operator's interactive UI feedback, show Balance and Available once, the account-page Add credit entry and a plain Pending holds section, without a disclosure/dropdown, internal account name, Enabled flag or raw duplicate balances. Keep the Service's complete snapshot and accounting schema unchanged internally; display every pending row with exact USD amounts, UTC dates, reservation/request key, timeout and terminal fields. No rows, expiration or idempotency fields are dropped. Do not recompute available credit or perform an additional accounting read for formatting.
- Existing ordinary-serving and `website-local` disabled-payment behavior stays unchanged. Hide the Add credit entry without an explicitly supplied payment capability. Old published bundles that lack the new top-up page fail closed rather than silently swapping in unrelated unrevisioned code.

## Deferred: polished Tor / JavaScript-disabled experience

Qualify readable typography/spacing and focus states, narrow/mobile layouts, clear denomination and payment-status navigation, semantic forms/disclosures, accessible recovery/error messages and behavior under slow/interrupted circuits in Tor Browser's restrictive settings. Preserve useful plain HTML forms and account snapshots without requiring client scripts.

This note does not authorize Tor infrastructure, onion endpoints, attestation changes, gateway edits or payment-method expansion. Our first-party no-JavaScript behavior and Stripe's separately hosted JavaScript-dependent Checkout are distinct boundaries; do not claim an end-to-end no-JavaScript card flow or Tor anonymity. A future payment path appropriate to that environment needs its own scope, privacy and acceptance decisions.
